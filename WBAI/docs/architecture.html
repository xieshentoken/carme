Carme：用一台闲置 MacBook 复刻 Grok Bot

把「常驻 AI 员工团队」从别人的云上搬回自己家里 —— 可行性、选型、架构、成本与路线。

2026-09-11　·　目标硬件 MacBook Pro 13" 2018（8GB / 可常驻）　·　开发机 MacBook Pro M1 Pro

00结论先行

三句话结论
  1. 能替代，而且替代品已经建好并在跑。项目代号 Carme，本机已验证：派活 → 主控拆解 → 派给成员 → 沙箱执行 → 回报 → 汇总，整条链路通。
  2. 瓶颈不是算力，是内存。8GB 机器做不了本地模型推理 —— 但这恰好不重要，因为推理本来就该走云端 API。它真正的价值是「24 小时在线」+「一个隔离的执行环境」。
  3. 两条路，先想清楚你要哪个。想要开箱即用、生态成熟，装 OpenClaw；想要极轻、完全可控、按自己的形状长，用 Carme。两条路都能把 Grok Bot 替掉。

唯一真正的硬骨头：账号代操作

Grok Bot 最值钱的地方，是它不依赖 API：直接登录你的账号，在界面层点击、填写、推进任务。这让它能操作那些永远不会有 API 的老系统 —— Salesforce 后台、招聘网站、内部报销系统。

自建方案里这块要自己补，技术栈是现成的：Playwright 已经预留在依赖里。缺的是三件事：

  • 凭证保管：登录态得加密存本地，且不能让模型直接看到密码（否则一次提示注入就泄露）。
  • 选择器稳定性：网站改版就会挂。要么用视觉定位（多模态模型看截图点坐标），要么用可访问性树而非 CSS 选择器。
  • 人在环审批：涉及付款、发送、提交这类不可逆动作，必须停下来等确认。
关于「用账号密码代登录」的风险

这件事的收益很大，风险同样大。建议分两步走：先只做只读类代操作（抓数据、查状态），把不可逆动作全部留给人工确认。等链路稳了再逐步放开写操作。

02硬约束：那台 2018 的真实边界

方案必须从硬件的真实数字长出来，而不是从愿望长出来。

硬件事实

项目实际情况后果
CPUIntel 双核 i5（2018 款 13" 低配）跑脚本够用，跑模型完全不行

为什么「不能跑本地模型」不是问题

很多人一想到自建 Agent 就想到本地跑大模型。在 8GB 机器上这条路是死的（7B 模型要 8GB 内存，加上系统直接爆）。
但反过来想：Agent 的瓶颈从来不是推理，而是工具调用和状态管理。推理交给云端 API，一次调用几分钱；本机只负责调度、沙箱、界面 —— 这些加起来内存占用不到 1GB。

而且云端 API 恰好解决了你原本的核心痛点：模型可换、额度不限。本地跑模型反而是把新的锁定换了个形式。

三条必须遵守的资源纪律

  1. 沙箱并发锁死为 1。一个容器 + 一个 Chromium 就能吃掉 1.5–2GB。同时开两个，8GB 机器开始疯狂 swap，整机卡到没法用。
  2. 任务并发可以放宽到 3。因为 LLM 调用是纯 I/O 等待，几乎不占本机资源。这个「任务并发 ≠ 沙箱并发」的区分是整个设计里最关键的一刀。
  3. 容器内存上限 2GB。colima start --cpu 2 --memory 4，容器内再限 2GB，给宿主留足余量。

为什么最终选「自建 Carme」

  1. OpenClaw 是强对手，但它不是为 8GB 机器设计的。它是 Node 全家桶 + pnpm workspace，Docker 沙箱，本体就不轻。更要紧的是它的多 Agent 是扁平隔离式（多个独立 agent 靠渠道绑定路由），官方文档明确说没有「主 Agent 指挥子 Agent」的层级机制 —— 而「一个主 Bot 带队」恰好是你的核心诉求。
  2. 你的诉求很集中。多角色 + 主控调度 + 一台执行机 + 手机端。不需要 20 个聊天渠道、不需要插件市场、不需要 MCP 全生态。为这些通用能力付出的资源代价，在 8GB 机器上是纯负担。
  3. 可控性就是可靠性。整个引擎不到 4000 行 Python，模型网关、Agent 循环、沙箱、调度全是你自己能读懂改动的代码。出问题时不用猜框架里发生了什么。
  4. 两条路不互斥。如果哪天想要 OpenClaw 的生态，Carme 的 agents.yaml 角色定义可以直接翻译过去；反过来也一样。不用现在就赌死。
什么情况下我建议你改用 OpenClaw

如果你发现：想要接微信/飞书/WhatsApp 这些现成渠道、想要社区插件市场、或者不想维护自己的代码 —— 那 OpenClaw 是更划算的选择。它的成熟度确实更高。
自建的价值只在「你愿意并且能够维护它」时才成立。

04架构

数据流：一次派活的完整生命周期

  1. 你在 PWA 里输入「调研三家竞品定价，做张对比表」，默认交给主控。
  2. API 层建任务记录 → 投给 Runtime → 立刻返回 task_id（不阻塞你的界面）。
  3. 主控用最强模型档位拆解目标，在一次回复里并发发起两个 delegate：情报员去查资料，工程师准备表格脚本。
  4. 每个成员在自己的循环里调工具。需要执行时向沙箱层申请槽位 —— 因为并发是 1，两个成员会排队，但这是刻意的（8GB 的物理限制）。
  5. 成员结果回传给主控，主控汇总成一份交付。过程中所有事件通过 SSE 实时推到你的界面。
  6. 你在任务详情里看到完整链路：每一步工具调用、每一条命令的真实输出、每个子任务的成本。

05关键设计决策

这几个决定，是「能在 8GB 上跑」和「跑不动」的分水岭。

① 角色绑「档位」，不绑具体模型

agents.yaml 里写 tier: reason；models.yaml 里 reason 档位挂一串候选模型，按顺序降级。第一个挂了自动换下一个。

这是对「模型锁定」最直接的回答。想换模型只改一处，所有 Bot 立刻跟着换。而且日常检索类任务用便宜档位、只有拆解和汇总用最强档位 —— 成本能压到 Grok Bot 的零头。

② 沙箱按需占用，等下属时主动让出

一个真实会踩的坑：主控占着唯一的沙箱槽位 → 派活给工程师 → 工程师也要抢这个槽位 → 主控等工程师、工程师等槽位 → 死锁。

解法是把「占用」和「持有」拆开：真要跑命令时才申请槽位，等待下属执行期间主动释放。在只有 1 个沙箱槽位的机器上，这是让多层协作能跑起来的关键。

③ 任务并发与沙箱并发分开限流

LLM 调用是纯 I/O 等待，开 3 个几乎不占本机资源；真正吃内存的是沙箱（一个容器 + Chromium ≈ 1.5–2GB）。

所以：任务并发 3，沙箱并发 1。如果笼统地「限制并发 = 1」，整个团队就退化成单线程，失去了「多 Bot 并行」的意义。

④ 派发是同步等待，不是消息队列

主控调用 delegate 时会一直等到子任务结束。好处是推理链路线性、可读、出错好定位；代价是子任务失败必须返回明确的失败文本，而不是让主控干等。

换来的是：任务详情里你能看到一棵完整的调用树，每个节点都有成本、耗时、真实输出。可观测性比理论上的吞吐量重要得多。

⑤ 前端不用构建工具

原生 ES 模块 + 手写 CSS，没有 npm install、没有 webpack。理由很实际：目标机器只有 8GB，多一个 node_modules 就多一份负担；而且你随时能打开源文件改两行。

手机端通过 PWA 实现 —— Safari 里「添加到主屏幕」就得到一个 App 图标，全屏运行，无需 App Store。

06成本模型

你选了「已有 API key，按量走」。下面是不同用量下的真实量级。

方案固定月费额度模型选择备注
Grok Bot · Cursor Teams Premium $120有周额度仅 Grok 约 ¥860/月，你当前的困境
Grok Bot · SuperGrok Heavy $300有周额度仅 Grok 约 ¥2160/月
Carme · 轻量用法 ¥0无任意 日常跑 DeepSeek/Qwen，约 ¥20–80/月 API 费
Carme · 主力用法 ¥0无任意 混合档位，关键任务上好模型，约 ¥150–400/月
省钱的真正杠杆是档位路由

一次「调研 + 写报告」的任务里，90% 的 token 花在检索、抽取、格式转换上 —— 这些用便宜档位（DeepSeek / Qwen / GLM）完全够。 只有主控的拆解和最终汇总值得上最强档位。
配好档位路由，成本大约是「全程用最强模型」的 1/5 到 1/10。

另外附送一个 Grok Bot 给不了的东西：每一分钱花在哪，界面上一清二楚。按 Bot、按模型、按任务都有明细，还能设日预算熔断（models.yaml 里的 budget.daily_usd），花超了直接拒绝新任务。

07落地路线

✓

阶段一 · 引擎跑通（已完成）

多 Bot 角色体系、主控派发、Agent 工具循环、可插拔沙箱、SQLite 持久化、REST + SSE、PWA 界面、部署脚本、假模型链路验证。全部在本机验证通过。

2

阶段二 · 接上真实模型，日常用起来

填 .env 里的 API key → 跑 models probe 看真实可用型号 → 调 models.yaml 的档位 → 把 allow_mock 改成 false。

先用它跑几天真实任务，观察三件事：哪些角色配得不对、哪些工具不够用、成本落在什么量级。这一步的目的是让配置从「我猜的」变成「我用出来的」。

3

阶段三 · 搬上那台 2018，变成真·常驻

在闲置机上跑 deploy/carme-node-setup.sh --docker（自动改电源策略、装容器运行时），然后二选一：

形态 A（推荐）：整套装在 2018 上，沙箱用 local。它插着电就一直干活，不依赖你在不在电脑前。
形态 B：Carme 留在 M1，2018 配成 remote 节点，重活丢给它。

再配 deploy/install.sh --service 注册开机自启，加上局域网访问，手机就随时能派活。

4

阶段四 · 补上 Grok Bot 的杀手锏

账号代操作：基于 Playwright 加一个 computer-use 工具，实现「登录 → 点按 → 填表 → 提交」。建议先做只读类，写操作一律留人工确认。

工作流录制：录下你的操作序列，抽象成可复用模板，Bot 照着执行并随纠正优化。

定时任务：让它每天早上自己拉数据、出简报，推到你手机上。

08风险与未完成项

诚实列清楚，免得踩空。

项目状态说明与应对
账号代操作（无 API 操作网站）未做Grok Bot 的杀手锏。Playwright 已预留，但要自己实现登录态保管与选择器策略。见阶段四
工作流录制与演化未做技术上可行（Playwright 录制 + 步骤抽象），但工作量不小
Bot 间网状通信有意不做星型拓扑在低配机上是更稳的选择 —— 网状通信会让并发数失控。需要时把成员也设成 can_delegate: true 即可，但建议先跑一段时间再开
多节点动态负载均衡未做目前按角色静态分配执行环境，不是动态调度
用户体系与权限极简只有一个 token，适合个人或小团队自用。别直接暴露到公网
提示注入行业未解Bot 会读网页，网页里可能藏指令。应对：工具权限按最小必要原则配（这就是为什么审校官只能读不能写），别给 Bot 配比你愿意交出去的权限更高的密钥
8GB 内存上限物理约束沙箱并发只能是 1，任务会排队。这是物理事实，不是配置问题
那台机器是笔记本需处理合盖/断电就中断。节点脚本会改电源策略，但必须插着电
最后一个判断

这套方案最大的风险不是技术，是维护意愿。自建意味着你拥有了全部的灵活性和全部的责任 —— 模型换版本、网站改结构、机器出故障，都得你自己处理。

如果你要的是「装上就不管了」，Grok Bot 或者 OpenClaw 更合适。如果你要的是「它按我的形状长，我随时能改」，那 Carme 这条路是对的 —— 而且现在已经能跑了。
